# transcript-qa — Q&A из транскриптов → MD + Google Doc

Извлекает содержательные вопросы и ответы из транскрипта и ведёт накопительный Q&A-файл. Один MD-файл на курс/проект, плоский список пар «вопрос → ответ». Google Doc обновляется только по явному запросу.

## Usage

```
/transcript-qa <путь-к-транскрипту>                      # только MD
/transcript-qa <путь-к-транскрипту> --gdoc               # MD + известный Google Doc проекта
/transcript-qa <путь> --md <путь-к-Q&A.md> --gdoc <url>  # явные цели
```

Без пути к транскрипту: спросить, какой транскрипт брать (или найти последний в `_TRANSCRIPTS/` по упомянутому проекту).

| AI Native (поток 2, Summer 2026) | `PROJECTS/13 AI NATIVE/02 Потоки курса/02 Summer 2026/Q&A — AI Native Поток 2.md` | `1QFkGiaJT52KDYCxcUgejoNIiKLuteKXsBi1W07QaS2U` (вставка `--after "Напишите ваш вопрос ниже"` — новые пары идут в самый верх основной секции, сразу под интро, «== АРХИВ ВОПРОСОВ ==» остаётся внизу нетронутым) |

Для нового проекта: спросить/предложить путь MD и (если нужен gdoc) попросить ссылку, затем **добавить строку в эту таблицу** (в обеих копиях SKILL.md: `~/.claude/skills/transcript-qa/` и vault `SKILLS/transcript-qa/`).

## Шаг 1 — Извлечение Q&A

Прочитать транскрипт целиком (для длинных — субагентом). Правила извлечения:

- **Включать:** вопросы участников голосом и озвученные из чата — про инструменты, AI, методологию, практику, а также значимую логистику (записи, расписание, доступы, бадди, Q&A-сессии).
- **Исключать:** технический шум («меня слышно?», «видно экран?»), приветствия, оффтоп.
- Вопрос — сжато, 1–2 предложения, с исправленными ошибками распознавания. **Имена спрашивающих в итоговый текст не выносить.**
- Ответ — **короткий и ёмкий, 1–3 предложения, от первого лица Алексея**, ничего не выдумывать. Если по логистике (запись, доступы, расписание) ответа не прозвучало — так и писать («ответ не прозвучал» / «обещали разобрать на следующей сессии»). Если содержательный вопрос остался без содержательного ответа — в Q&A не включать (см. Шаг 1.5).
- **Стиль ответов — как Алексей пишет сам** (эталон — секция «1 поток» в Q&A-доке AI Native): прямой заход с «Да / Нет / Можно / Нужно», разговорно и практично, конкретные инструменты с доменами (telegram.org, fathom.video), варианты списком («Два варианта: …»), дефис «-» вместо длинного тире, буква «е» вместо «ё», без болда и канцелярита.
- Язык — русский (или язык транскрипта).

## Шаг 1.5 — Фильтр значимости

Перед записью в MD/gdoc оценить каждую извлечённую пару на самостоятельную ценность — не всё, что формально было вопросом, стоит фиксировать в накопительном файле.

- **Не включать:**
  - тривиальные факты без практической пользы (очевидное, легко гуглящееся, не специфичное для Алексея/курса) — например, «в каком формате Obsidian создаёт файлы?» → «MD»;
  - реплики-уточнения без самостоятельной ценности вне контекста разговора («а точно тысячи?» → «нет, штук 15»);
  - содержательные вопросы, оставшиеся без содержательного ответа («разберём в следующий раз») — см. исключение для логистики выше.
- **Включать:** методология, принципы работы, конкретные инструменты с объяснением use-case, практические лайфхаки — то, что несёт информацию, которую читатель не знал бы и так, и полезно вне исходного разговора.
- Тест: если ответ не добавляет ничего сверх общеизвестного и не имеет пользы сам по себе (вырванный из контекста разговора) — не включать.
- После первичной сборки списка пар — явно пройтись по нему этим фильтром и отсеять слабые, прежде чем писать в MD/gdoc.

## Шаг 2 — Обновление MD-файла

1. Перечитать MD-файл непосредственно перед правкой (Obsidian sync). Если файла нет — создать с заголовком `# Q&A — {проект}` и одной строкой описания.
2. **Дедупликация:** сравнить новые вопросы с уже существующими в файле по смыслу (не по точному тексту). Уже отвеченные — пропустить; если новый ответ существенно дополняет старый — обновить существующий блок.
3. Формат — плоский список без секций по сессиям: вопрос — list item 1-го уровня, ответ — list item 2-го уровня (отступ **4 пробела**), без болда и без имён. Новые пары вставлять **сверху** списка (сразу после заголовка и строки-описания), а не в конец — самые свежие вопросы должны быть первыми при открытии файла. Если добавляется несколько пар за один запуск — порядок между ними как в транскрипте (хронология разговора), но весь блок целиком ставится выше уже существующих пар:

```markdown
- Вопрос?
    - Ответ.
```

## Шаг 3 — Google Doc (только по запросу)

Обновлять gdoc только если Алекс явно попросил (сказал «и в гугл-док», передал ссылку, либо `--gdoc`).

Python: `~/.config/hermes/venv/bin/python ~/.claude/skills/transcript-qa/gdoc_qa.py`
Auth: токен gdrive-admin (`~/.config/gdrive-admin/token.json`, полный drive-scope). Если токена нет: `gdrive-share-admin/gdrive_perms.py auth`. Docs API в Cloud-проекте выключен, поэтому скрипт работает только через Drive API: чтение = export, запись = HTML-roundtrip (export HTML → вставка блока → re-upload). Комментарии в доке roundtrip не переживают; перед записью скрипт сам сохраняет docx-бэкап в `~/.cache/transcript-qa/backups/`, плюс работает нативная version history дока.

1. `gdoc_qa.py read --doc <url-или-id>` — получить текущий текст дока.
2. Дедупликация по смыслу против текста дока: докидывать **только новое**.
3. Записать JSON в scratchpad (`{"items": [{"q","a","asker","time"}]}` — **без** `title`, заголовки сессий в док не добавляем) и выполнить `gdoc_qa.py append --doc <id> --json qa.json --after "<текст интро/заголовка секции>"` — блок вставится сразу под этим текстом, то есть в самый верх секции, выше уже существующих пар (для AI Native: `--after "Напишите ваш вопрос ниже"`). Так новые вопросы всегда оказываются первыми при открытии дока. `--before "<заголовок>"` (вставка в конец секции, перед следующим заголовком) остаётся доступной опцией для случаев, когда порядок специально должен быть хронологический снизу-вверх. Без флагов — в конец дока. Формат вставки: настоящий вложенный список (● жирный вопрос / ○ ответ вторым уровнем), без имён.
4. Если всё уже есть в доке — ничего не дописывать, сообщить об этом.
